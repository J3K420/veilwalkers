# Story 5.3: Grant and consume the Guaranteed-Rare Lure

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player who bought the Veil Pack,
I want a guaranteed Rare-or-better Lure,
So that the top pack delivers a distinct, premium outcome.

## Acceptance Criteria

**AC-1 (a Veil Pack purchase grants a `GuaranteedRareLure` one-shot item ALONGSIDE the Credits, stored in `SaveModel`'s one-shot inventory, exactly once).**
**Given** a Veil Pack purchase
**When** it is reconciled
**Then** a `GuaranteedRareLure` one-shot item is granted alongside the Credits and stored in `SaveModel`'s one-shot inventory.
[Source: docs/epics.md#Story-5.3 (lines 806-808); docs/architecture.md:496-497 (`PurchaseReconciler` grants exactly once keyed by Play order id), :522 (the purchase data flow). **The grant happens inside `PurchaseReconciler` — the SAME exactly-once engine + order-id dedup Story 5.2 built (PurchaseReconciler.cs). The one-shot item is granted ONLY when the granted pack carries `CreditPack.IncludesGuaranteedRareLure == true` (the Veil pack — CreditPack.cs:52-57, set true ONLY for Veil in CreditPackCatalog). The store is a NEW `int SaveModel.GuaranteedRareLures` counter (the `StrongCaptureCharges`/`StabilityBoostCharges`/`NightveilFilterCharges` counter precedent — NOT a list, NOT a `ChargeType`), granted in the SAME atomic write as the Credits grant so the exactly-once `Granted`-state advance covers BOTH Credits AND the lure (a kill between the two would otherwise grant one without the other). The 5.1/5.2 deferral "the Guaranteed-Rare Lure grant is Story 5.3" lands here.]**

**AC-2 (consuming the Guaranteed-Rare Lure resolves through the existing `LureSystem` path, filters the spawn pool to `Rarity >= Rare`, spawns a Rare-tier-or-better Monster, and consumes the item EXACTLY ONCE).**
**Given** the player consumes the Guaranteed-Rare Lure
**When** it resolves through the existing Lure path (`LureSystem`)
**Then** the spawn pool is filtered to `Rarity >= Rare` and a Rare-tier-or-better Monster spawns
**And** the item is consumed exactly once.
[Source: docs/epics.md#Story-5.3 (lines 810-813); docs/architecture.md (the encounter Lure path — `EncounterService.TryLureAsync` → `LureSystem`). **The consume routes through the EXISTING Lure path: a NEW `LureKind.GuaranteedRare` (the reserved-but-undefined enum value — LureKind.cs:6-9 doc "Story 5.3 adds `GuaranteedRare`") flows through `EncounterService.TryLureAsync(LureKind.GuaranteedRare)` exactly like Basic/Premium/Multi. The spawn-pool filter is the EXISTING `LureSystem.RollOne` partition on `def.Rarity >= RarityThresholds.GuaranteedRareFloor` (= `Rarity.Rare`, INCLUSIVE — Rarity.cs:41-53, LureSystem.cs:147-180), but the Guaranteed-Rare roll FORCES the rare-or-better side (NOT a probabilistic `rareChance` roll) and does NOT fall back to the common pool (the guarantee is a CONTRACT, not a probability — distinct from `RollOne`'s MVP-roster fallback). The item is consumed (the counter decrements by ONE) ATOMICALLY in the same composed write as the Lure — NOT Credits (cost 0; the pack already paid). Exactly-once = the same guarded-decrement-then-persist-or-rollback discipline as `ProgressionService.TryConsumeChargeAsync` (ProgressionService.cs:302-364): a zero-inventory consume is a typed failure that persists nothing; a successful consume decrements once under the shared lock + persists once + rolls back on fault.]**

### The design decisions this story locks (call them out for the CR reviewer)
1. **The one-shot lure grant rides the existing `Granted`-state persist (Decision C).** Rather than a second persist after the Credits grant, increment `GuaranteedRareLures` in the SAME write that advances the `PendingPurchaseRecord` to `Granted` (`PurchaseReconciler.AdvanceToGrantedAsync`). NOTE the method takes only `orderId` today — the Veil flag must be THREADED IN as a new bool param (read `pack.IncludesGuaranteedRareLure` at the PurchaseReconciler.cs:348 call site, where `pack` is in scope; it is NOT in scope inside `AdvanceToGrantedAsync`). The persisted `Granted` state — already the 5.2 exactly-once primary guard — becomes the lure's exactly-once envelope too: a `Granted` record has, by definition, already granted both the Credits AND the lure. No new "lure-granted" flag, no split write; the lure shares the SAME narrow grant↔state-advance window 5.2 already documents (deferred to the Phase-2 verifier).
2. **A plain `int` counter, not a `ChargeType` (Decision B).** `GuaranteedRareLures` is a purchased one-shot item — it gets `SaveModel.GuaranteedRareLures` + its own consume, NOT a `ChargeType` enum value (which is the XP-EARNED family — StrongCapture/StabilityBoost/NightveilFilter). Routing it through `ChargeInventory` would conceptually allow it to be granted by leveling, which contradicts the canon (it is Veil-pack-only).
3. **The forced Rare+ roll has NO common fallback (Decision E).** `RollOne` falls back to the whole populated set when the rare-or-better side is empty (the MVP-roster graceful degrade). The GUARANTEE cannot degrade — `RollGuaranteedRare` picks ONLY from the Rare+ subset and reports a typed failure if that subset is empty (a content error), so the consume can refuse and KEEP the player's lure rather than silently spawning a Common.
4. **A distinct `NoGuaranteedRareLure` failure reason, NOT `InsufficientCredits` (Decision H).** A zero-inventory consume is a "you have no lures" state, not a "you can't afford it" state — surfacing it as a credit shortfall would (wrongly) prompt the Shop top-up sheet (AR-11). You cannot buy a single lure (only the Veil pack), so the affordance is fundamentally different.
5. **The consume substitutes the credit spend in `TryLureAsync` and obeys every existing safety rail (Decision F/G).** Placement is secured BEFORE the consume (a NoPlacement costs nothing); the consume is the atomic write (one persist, AR-8); a post-consume spawn refusal refunds the lure ("no charge without a spawn" — the `RefundLureSpendAsync` parity); an empty rare-pool keeps the lure. Same shape as the 4.2 credit-spend Lure, with the one-shot item standing in for Credits.
6. **No new assembly edge (Decision I).** The grant is in `Veilwalkers.Billing` (already references Economy + Persistence). The consume seam is in `Veilwalkers.Economy` / the field is in `Veilwalkers.Persistence`; `Veilwalkers.Encounter` already references Economy + Monsters + Persistence; `LureKind`/`LureSystem`/`RollGuaranteedRare` are all in `Veilwalkers.Encounter`. NO `.asmdef` change, NO `AcyclicDependencyTests` matrix edit (contrast 5.2, which DID need the Billing→Persistence edge).
