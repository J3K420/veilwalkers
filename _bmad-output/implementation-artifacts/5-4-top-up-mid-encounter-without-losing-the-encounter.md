# Story 5.4: Top up mid-encounter without losing the encounter

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to buy Credits during an encounter and return to the exact same moment,
So that spending feels like buying more fun, not unblocking a wall (UJ-2).

## Acceptance Criteria

**AC-1 (an insufficient-credit Lure/Slay attempt surfaces the top-up seam over a LIVE encounter — the world does not lock).**
**Given** an insufficient-credit Slay (or future re-Lure) attempt in a live encounter
**When** `OnInsufficientCredits` fires
**Then** the encounter stays LIVE (the state machine resolves back to `Lured`, the spawns are NOT released, the world does not lock), and the rejected-spend event carries enough for App/UI to present a non-blocking top-up sheet "one level deep" over the encounter.
[Source: docs/epics.md#Story-5.4 (lines 823-825); docs/architecture.md:524 (Shop round-trip), UX-DR13 (lines 106 — the non-blocking top-up sheet over the live encounter). **The MID-ENCOUNTER credit-spend trigger is SLAY, not Lure.** A `Lure` requires `State == Idle` (one Lure per encounter — EncounterService.cs:230), so an insufficient-credit *Lure* fails FROM Idle and leaves the machine Idle — that is NOT a "live encounter" top-up (the epic's "Lure/Slay" is generic; for 5.4's LIVE-encounter scenario only SLAY applies today, with a future re-Lure flow joining it). The Slay path is ALREADY correct: an `InsufficientCredits` Slay goes `Lured → Acting → Resolving` then `CompleteResolve()` resolves it BACK to `Lured` (EncounterService.cs:1038-1041 — success OR not-PersistenceFailed → CompleteResolve) WITHOUT releasing spawns, then raises `OnInsufficientCredits` (EncounterService.cs:1050-1052, AR-11 — the service NEVER opens the Shop). 5.4 must PROVE this with a regression pin (after an insufficient-credit SLAY the encounter is STILL `Lured`, spawns intact, the world does not lock) and must NOT regress it. The actual top-up SHEET (the pixels + the one-level-deep stacking) is the Epic 6 / 6.3 `AppStateMachine` consumer — the UI-presenter altitude split. 5.4's AC-1 contribution is the headless GUARANTEE that the encounter survives the rejected attempt.]**

**AC-2 (after a purchase from the top-up sheet, the player returns to the EXACT SAME encounter, state-faithful — lured Monsters, per-monster scan progress, applied boosts intact).**
**Given** the player buys a pack from the top-up sheet
**When** the purchase completes
**Then** Credits update immediately (the existing 5.1/5.2 grant path) and the player returns to the exact same encounter, state-faithful: the lured Monster id(s), per-monster scan progress, and applied boosts are intact.
[Source: docs/epics.md#Story-5.4 (lines 827-829); docs/architecture.md:415 (`EncounterSnapshot.cs` stores AnchorTokens + per-monster STATE, not live refs), :524 (snapshot before Shop, rehydrate on return). **This is the CORE 5.4 build: a `EncounterService.SnapshotActiveEncounter()` capture + a `EncounterService.RehydrateFromSnapshot()` restore, round-tripping through `SaveModel.EncounterSnapshot` (the reserved field, SaveModel.cs:81-86) via the `EncounterSnapshotData`/`EncounterMonsterStateData` DTOs (EncounterSnapshotData.cs, EncounterMonsterStateData.cs — both reserved-but-unserialized today). "State-faithful" = the rehydrated encounter has the same state-machine state, the same `_activeAnchors`, the same lured Monster id(s), the same `_scannedThisEncounter`, and the same `_activeExtras` as before the Shop trip. The Credits-update-immediately half is already done (5.1/5.2 `PurchaseReconciler` → `CreditService` grant); 5.4 adds the encounter SURVIVAL half.]**

**AC-3 (the Shop round-trip snapshots the active encounter to memory + disk before Shop and rehydrates it on return/relaunch; the AR Safety Warning does NOT re-fire on resume).**
**Given** the Shop round-trip
**When** the player leaves to Shop and returns
**Then** the active encounter (anchors + per-monster state) is snapshotted to memory + disk before Shop and rehydrated on return/relaunch
**And** the AR Safety Warning does NOT re-fire on resume.
[Source: docs/epics.md#Story-5.4 (lines 831-834); docs/architecture.md:524-525 (AppStateMachine snapshots before Shop, rehydrates on return, Safety Warning does NOT re-fire). **The snapshot-to-disk is the ONE atomic persist `SnapshotActiveEncounter` does (AR-8): write `SaveModel.EncounterSnapshot` under the shared lock, ONE `SaveAsync`. "Rehydrate on return" = in the SAME process (the snapshot is also held/derivable in memory); "rehydrate on relaunch" = on launch, if `SaveModel.EncounterSnapshot != null`, `RehydrateFromSnapshot` reconstructs the in-memory encounter. The "AR Safety Warning does NOT re-fire" half is ALREADY satisfied by Story 3.2: `ArSafetyGate.RequestEntry(ArEntryKind.ShopResume)` skips straight to `Acknowledged` without burning the once-per-session full read (ArSafetyGate.cs:73-98). 5.4 does NOT re-implement the gate — it must NOT break it; the WIRING of "a Shop resume calls `RequestEntry(ShopResume)` not `ColdEntry`" is the Epic 6 / 6.3 `AppStateMachine` navigation decision (deferred). 5.4 records the snapshot/rehydrate engine + a note that the resume-uses-ShopResume wiring is 6.3's.]**

**AC-4 (an app-kill mid-purchase rehydrates the EXACT encounter on relaunch AND the purchase reconciles exactly once — the 5.2 engine).**
**Given** an app kill mid-purchase
**When** the app relaunches
**Then** the snapshot rehydrates the exact encounter AND the interrupted purchase reconciles exactly once (Story 5.2 `PurchaseReconciler.ReconcilePendingOnLaunchAsync`).
[Source: docs/epics.md#Story-5.4 (lines 836-838); docs/architecture.md:510 (NFR-4 exactly-once), :524 (snapshot rehydrate on relaunch). **The two halves are INDEPENDENT and both already-or-newly covered: (a) the purchase-reconciles-exactly-once half is the EXISTING 5.2 `PurchaseReconciler.ReconcilePendingOnLaunchAsync` launch-recovery pass (PurchaseReconciler, wired in Bootstrap's post-load `ContinueWith`) — 5.4 adds NO new reconcile logic, it only PROVES the two are compatible (a relaunch with BOTH a pending purchase AND an encounter snapshot recovers both, independently); (b) the snapshot-rehydrates-the-exact-encounter half is 5.4's new `RehydrateFromSnapshot` driven on launch. The pin is a single test: persist an encounter snapshot + a pending purchase, simulate a relaunch (new services over the same stored model), assert the encounter rehydrates state-faithful AND the pending purchase grants exactly once (the credits land once, the snapshot's monsters/boosts restore).]**

### The design decisions this story locks (call them out for the CR reviewer)
1. **The lured Monster id(s) get a field (`_activeMonsterIds`), index-parallel to `_activeAnchors` (Decision A).** They were built locally + discarded; the snapshot needs them. Purely additive book-keeping; the `LureResult` is byte-identical.
2. **The snapshot carries the state-machine state as a STABLE STRING tag, NOT the raw enum int (Decision B).** The `AppliedBoosts`/`ChargeType`-stability precedent — a string tag survives an enum renumber. Mapped via an explicit switch.
3. **`_activeExtras` round-trips at the ENCOUNTER level (`EncounterSnapshotData.AppliedExtras`), not per-Monster (Decision C).** `_activeExtras` is an encounter-wide `HashSet<ExtraKind>` (the 4.6 "for the remainder of the encounter" model), so an encounter-level snapshot field matches reality — cleaner than redundantly storing it on every Monster entry. The per-Monster `AppliedBoosts` stays reserved for a future per-monster boost mechanic.
4. **`ScanProgress` round-trips the 4.3 boolean as 0.0/1.0 (Decision C).** 4.3's scan-state is boolean-grained ("scanned this encounter"); the DTO's `float [0,1]` carries it as 0.0/1.0. A fractional scan mechanic is still a future story.
5. **Snapshot ONLY from `Lured`; rehydrate ONLY from `Idle` (Decisions E/G).** The Shop top-up happens between actions (the encounter is `Lured`). Snapshot from `Resolving` would deadlock (the lock is held); from `Idle`/`Resolved` there is nothing to snapshot. Rehydrate is a from-Idle restore (like `BeginLure`); it never clobbers an active encounter.
6. **Snapshot is consumed once — cleared on successful rehydrate (Decision G).** Once restored, the live encounter is the source of truth (re-snapshotted on the next Shop trip). A second rehydrate is a no-op. `ClearEncounterSnapshot` handles the normal-end clear (the App-tier wiring is 6.3's).
7. **Restore the LOGICAL encounter; the scene re-spawn/re-anchor RENDER is 6.3 (Decision G).** The `Recover` "scene re-anchor is Story 6.3" precedent + the 4.7 render-defer altitude split. `_activeSpawnHandles` is process-local (released on teardown) — NOT restored from the snapshot; the visual re-spawn is 6.3.
8. **Corrupt/partial snapshot is a typed no-op, never a crash (Decision H, NFR-3).** Empty Monsters / unrecognized State / null inner collections (repaired by `CoerceNullCollections` on load) → clear + `GameLog.Error` + return false. The player loses an interrupted encounter (a corruption edge), the app never crashes.
9. **No new assembly edge, no schema bump (Task 2/7).** The DTOs live in `Veilwalkers.Persistence`, which `Veilwalkers.Encounter` already references. The DTO field additions are additive (no shipped save wrote an `EncounterSnapshot`). NO `AcyclicDependencyTests` matrix edit (contrast 5.2's Billing→Persistence edge), NO `SaveMigrations` change.

### Edge cases & boundary rules (must-handle — these become test cases)
- **Snapshot a `Lured` encounter (AC-2/AC-3):** captures Monster id(s) + per-id scan flag (0/1) + applied extras (tags) + the `Lured` State + anchors; ONE persist.

- **Rehydrate from a persisted snapshot (AC-2/AC-3):** restores state-faithful (anchors + ids + scan + extras + State), drives Idle→`Lured`, clears + persists the consumed snapshot.
- **Rehydrate with `EncounterSnapshot == null`:** no-op, false, NO write (the common launch — no active encounter).
- **Rehydrate over an already-active encounter (State != Idle):** no-op, false + warn (never clobber).
- **Rehydrate a corrupt snapshot (empty Monsters / unrecognized State):** clear + `GameLog.Error` + false (NFR-3, never throw, never a half-encounter).
- **Snapshot consumed once:** a second rehydrate is a no-op (snapshot already cleared).
- **Relaunch recovers BOTH (AC-4):** a stored snapshot + a pending purchase → a fresh reconciler grants the purchase once AND a fresh service rehydrates the encounter, independently.
- **The world does not lock (AC-1):** an insufficient-credit Lure/Slay leaves the machine `Lured` + spawns intact + `OnInsufficientCredits` raised (the 4.2/4.5 regression pin).
- **`EndEncounter` clears `_activeMonsterIds`:** parity with `_activeAnchors`/`_activeSpawnHandles`.
- **No migration:** an existing save with `EncounterSnapshot == null` is unaffected; the additive DTO fields default safely.
