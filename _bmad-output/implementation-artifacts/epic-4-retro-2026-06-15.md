## 3. Recurring patterns — the real lessons

### Lesson 1 — One atomic-write primitive, six siblings: the pattern compounded one tier deeper than Epic 3 predicted
4.1 built `CommitActionAsync` as a *representative* composed write, then every subsequent story added a **sibling** with a different delta shape but the identical skeleton (shared lock once / capture ref once / mutate-in-memory / ONE `SaveAsync` / recovery-swap guard / whole-mutation rollback): 4.2 spends credits, 4.3 touches neither (free), 4.4 adds the lock-free `StageXpGrant` seam so charge+codex+XP commit in one save, 4.5 nets credits+codex+XP, 4.6 nets charge+in-memory-modifier. The load-bearing invariant — **"one transactional write per player action" (AR-8 / architecture.md:644)** — held across all six, and the recurring CR theme was *protecting* it (4.4's "no duplicate StrongCapture event"; 4.5's "no free-Slay via two persists"; the consistent "deduct/consume only on the real outcome, roll back on fault"). **Takeaway:** when an epic's stories are N variations of one transactional action, invest the CR budget early (4.1/4.2 took 31/35 raw findings) to harden the primitive; the later siblings inherit the correctness and their CR load drops.

### Lesson 2 — The "pin the behavior / inequality, defer the magnitude" discipline kept balancing out of the code
Every tunable in the epic landed as a **local `const` on its system, with the AC pinned as a strict inequality or a band — never as an `EconomyConfig` field**: `LureSystem.BasicRareChance < PremiumRareChance` (4.2), `CaptureSystem.BaseCaptureChance < StrongCaptureChance` (4.4), `SlaySystem.SlaySuccessChance` between them + `XpPerSlay > XpPerCapture` (4.5), `ExtrasSystem` ease/boost `> un-boosted` clamped `< 1.0` (4.6), and 4.7's per-tier durations monotonic-and-within-band. This is one coherent decision repeated 5×: the AC is the *relationship*, not the number; adding SO fields would widen `EconomyConfig.SetForTests` and need more `InternalsVisibleTo`. **13 OQ-9 "the value is provisional" deferrals** now sit in the ledger, all owned by the balancing pass. **Takeaway:** a strict-inequality test is mutation-testable and balancing-proof; the exact number is a tuning artifact that doesn't belong in the test or the config yet.

### Lesson 3 — Typed result + distinct failure reason, never an exception, never a misleading code
4.1 left a documented wart: an out-of-sequence `RunActionAsync` returned `PersistenceFailed`+0 (a lie — nothing persisted). Each later story *settled it for its own path* with a distinct `NotSettled` reason (4.3 Scan, 4.4 Capture, 4.5 Slay, 4.6 extras), and every action returns a typed `*Result` carrying exactly what the HUD needs ("missed — retry" vs "can't — no charge / not enough Credits / not settled"). The taxonomy got richer with each story and the CR consistently rewarded the precision (4.2's 9 patches were largely the typed-failure taxonomy: `NotAttempted`/`AlreadyActive`/refund-reports-`Failed`). **Takeaway:** a deferral that documents a *known* imprecise error is a fair IOU — but it must name the owner, and each owner must actually settle it (they did).

### Lesson 4 — The struct-invariant trap: a `default`-constructed value type silently violates its contract
4.7's CR found (and a 4.x-wide pattern echoes) that a `readonly struct` with a public constructor and ctor-set invariant fields is a lie for `default(T)` — the zero value bypasses the ctor (null strings, false "always true" flags). The fix, applied via the `LureResult` precedent: **private ctor + an internal factory** (so only the authority builds it) **+ invariants as constant *properties*, not ctor-set fields, + null-safe getters** — so even `default(T)` honors the contract. **Takeaway:** any value type with an "always X" invariant must express it as a computed property, not a field the ctor sets; and constructible-only-by-the-decision-owner (factory) prevents a future second caller from building a contradictory instance. This generalizes the `LureResult`/`ScanResult` factory discipline already in the codebase.

### Lesson 5 — The UI-presenter altitude split absorbed a VFX-heavy story without a single pixel
4.7's ACs read as pure animation/shader work (tiered entrances, camera glitch, ambiance), yet it shipped as a headless pure-logic `MaterializationPresenter` + value types + an inert view, with all render deferred to Epic 6 — because **there is no AR rig scene yet** and the `[[ui-presenter-pattern]]` (from 2.4/2.5) is settled. The scope call was made explicitly at the create-story gate, not discovered mid-dev. This is the same discipline Epic 3 held for its four AR-HUD views. **Takeaway:** when a story's ACs are written in render language but the rig doesn't exist, the testable kernel is the *decision* (what entrance, how long, when the bar shows, how reduced-motion tames it, that the duration never gates the spend-ack); the pixels are a separate, honestly-deferred story.

Worth scoping 5.4 deliberately — it is the Encounter equivalent of the 6.3 AR-rig convergence point.
- ⚠️ **Billing is the first real external-SDK + platform-store dependency.** Unity IAP / Play Billing has no EditMode equivalent — it will need the same seam/adapter split the AR epic used (a pure-logic `PurchaseReconciler` decision tested against a fake `IBillingService`, the real Play adapter `#if UNITY_ANDROID` stubbed-and-deferred). - ✅ **No Epic-4 discovery invalidates Epic 5's plan or architecture.** Epic 4 delivered its seams in the shape Epic 5's ACs assume. **Epic update NOT required.**
