# Story 4.2: Lure a Monster (Basic / Premium / Multi)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to spend Credits to summon Monsters (Basic / Premium / Multi-Lure),
So that I have something to hunt.

## Acceptance Criteria

**AC-1 (cost shown before spend; sub-second spend-ack; deduct ONLY on successful spawn — a failed spawn does not deduct / is refunded).**
**Given** sufficient Credits and a detected plane
**When** the player chooses Basic (1), Premium (4), or Multi-Lure (5)
**Then** the cost is shown before the spend, the spend-ack confirms sub-second on the credit pill, and Credits deduct only on successful spawn (a failed spawn does not deduct / is refunded).
[Source: docs/epics.md#Story-4.2 (AC-1, lines 626-628); docs/architecture.md:61-63 (cost table — Basic 1 / Premium 4 / Multi 5), :644-649 (AR-8 one atomic write per action — the deduct+spawn commit together; failed spawn = no persisted deduction), :313-314 (SpendResult typed result), :48 (NFR-2 sub-second spend-ack ≠ materialization duration). CLAUDE.md Economy canon: Basic Lure 1 · Premium Lure 4 · Multi-Lure 5.]

**AC-2 (Premium's rare-tier probability is STRICTLY higher than Basic's).**
**Given** Premium vs Basic Lure
**When** rarity is rolled
**Then** Premium's rare-tier probability is strictly higher than Basic's.
[Source: docs/epics.md#Story-4.2 (AC-2, lines 630-632); docs/architecture.md:62 (Premium = "Higher rare chance"), :702 (Premium keeps its probabilistic higher-rare-chance; only the Guaranteed-Rare Lure FORCES the tier floor — that forced floor is Story 5.3, NOT 4.2), :687-690 (ordered Rarity enum + the named `Rare` threshold).]

**AC-3 (Multi-Lure spawns two Monsters in one encounter; RESOLVED FLAG — require two placements, block with coaching + NO charge if fewer than two are available; never silently drop or double-charge).**
**Given** Multi-Lure
**When** it resolves
**Then** two Monsters spawn in one encounter; **if two valid placements are not available, the Multi-Lure is blocked with coaching and NOTHING is deducted** (the deduct-only-on-successful-spawn rule of AC-1 applied to the whole Multi-Lure) — never silently drop a monster and never double-charge.
[Source: docs/epics.md#Story-4.2 (AC-3, lines 634-636 — the `[FLAG: confirm desired behavior with PM]`); docs/architecture.md:665-667 (the same FLAG — "spawn what fits + queue/relocate the second; do not silently drop or double-charge"). **FLAG RESOLVED (PM decision, 2026-06-14): require-2-placements-or-block.** Pre-check that two valid placements exist BEFORE the spend; if fewer than two are available, refuse the Multi-Lure with the plane coaching message and deduct nothing — this is the cleanest AC-1 parity (no half-charge, no pending-spawn queue, never strands the player). The "spawn-what-fits + queue/relocate the second" wording in epics/architecture is SUPERSEDED by this decision; feed it upstream into epics.md:636 + architecture.md:665-667 (UX feed-upstream queue [[ux-feed-upstream-queue]]).]

**AC-4 (insufficient Credits → Lure blocked + `OnInsufficientCredits` raised; the world does not lock).**
**Given** insufficient Credits
**When** the player attempts a Lure
**Then** the Lure is blocked and `OnInsufficientCredits` is raised (App/UI decides the top-up prompt); the world does not lock.
[Source: docs/epics.md#Story-4.2 (AC-4, lines 638-640); docs/architecture.md:478-480 (AR-11 — services NEVER open the Shop or call Billing/UI; they raise `OnInsufficientCredits`; App/UI decides), :607 (world never locks at zero; only Lure is dimmed with its real cost shown). This is the FIRST credit-spending caller of the `EncounterService.OnInsufficientCredits` seam built (un-exercised) by Story 4.1.]

### The design decisions this story locks (call them out for the CR reviewer)
1. **The credit-spend composed write copies the 4.1 atomic-write pipeline, mutating `model.Credits` directly under the SHARED `SaveMutationLock` (Decision D).** A Lure spends credits (not charges) and records NO codex discovery, so it is a sibling of `CommitActionAsync`, not the same call. It does NOT call `CreditService.TrySpendCreditsAsync` (that takes its own lock → deadlock; the architecture's whole point of the shared lock is one serializing gate — deferred-work.md:6, [[codex-service-lock-tier]]). ONE `SaveAsync`, recovery-swap guard, whole-mutation rollback (restore `model.Credits`), events after release.
2. **Deduct ONLY on successful spawn (AC-1 / AR-8) via the pre-check-then-persist ordering (Decision E).** Placement capacity is secured BEFORE the persisted deduction (a placement failure costs nothing); credits are checked BEFORE the deduction (insufficient → `OnInsufficientCredits`, nothing persisted); only when both hold does the ONE persist deduct, then the spawn activates. A post-deduction spawn failure (NFR-3 path) refunds via the rollback. No charge-without-spawn, no spawn-without-charge.
3. **`LureSystem` is the architecture-named home (architecture.md:416, :701) for cost + rarity roll, pure + side-effect-free (Decision A/B/C).** Cost from `EconomyConfig` (never hard-coded, AR-16); the rare-tier boundary from `RarityThresholds.GuaranteedRareFloor`; the STRICT Premium>Basic inequality is the AC, the numbers are OQ-9 provisional. `LureSystem` decides; `EncounterService` spends/persists/spawns.
4. **`IRandom` is a NEW Core seam (the `IClock` precedent), because no RNG exists and AR-18-style determinism forbids ambient `UnityEngine.Random`/`System.Random` in logic.** Production `SystemRandom`; deterministic `FakeRandom` in tests pins the rarity-roll boundary exactly.
5. **Multi-Lure = require-2-or-block (Decision in AC-3 — the RESOLVED `[FLAG]`).** Two valid placements required; fewer than two → block + coach + deduct nothing + release any provisionally-secured placement. The "spawn-what-fits + queue" epics/architecture wording is SUPERSEDED and fed upstream. Cleanest AC-1 parity; no pending-spawn queue (that complexity is explicitly rejected).
6. **AC-4 settles the 4.1 `OnInsufficientCredits`-no-caller deferral.** `TryLureAsync` is the first credit-spending caller; it raises the existing `EncounterService.OnInsufficientCredits` (never opens Shop — AR-11). Slay (4.5) is the second; Epic 6 binds the event.
7. **The render is 4.7 (decision: logical-spawn-now, cinematic-later).** 4.2's spawn is the pool-activate + anchor + state machine; the tiered T1–T5 entrance + the spend-ack-≠-materialization-duration (NFR-2) animation is Story 4.7. The `SpendResult` is the sub-second ack contract (synchronous after persist), not a measured-ms test.

8. **SANCTIONED DEVIATION from Decision F — `TryLureAsync` returns `Task<LureResult>`, not `Task<SpendResult>`.** Decision F's lean named `Task<SpendResult>`, but a Lure produces MORE than a spend outcome: it must report the spawned Monster id(s) (for the deferred 4.7 materialization) and a Lure-specific failure taxonomy (no-placement / already-active vs the pure economy reasons). So the action returns a richer `LureResult { Success, FailureReason (LureFailureReason), Spend (SpendResult), SpawnedMonsterIds }` that EMBEDS the `SpendResult` (the sub-second ack value is `LureResult.Spend.NewBalance`). This is a superset of Decision F's contract — every consumer that wanted the `SpendResult` reads `result.Spend` — chosen so the Lure result is self-describing without a side-channel for the spawned ids. `LureFailureReason` distinguishes `NoPlacement` / `InsufficientCredits` / `PersistenceFailed` / `AlreadyActive`; the embedded `SpendResult` on a pre-spend block carries `SpendFailureReason.NotAttempted` (a new appended reason — the spend never ran, distinct from a balance shortfall or an I/O fault).
