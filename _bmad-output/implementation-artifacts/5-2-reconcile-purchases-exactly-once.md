# Story 5.2: Reconcile purchases exactly once

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want every pack I pay for granted exactly once even if something interrupts the purchase,
So that I'm never charged without Credits or granted twice.

## Acceptance Criteria

**AC-1 (the `PurchaseReconciler` sequence is: write pending-ledger → acknowledge → credit exactly once keyed by Play order id → persist → clear pending).**
**Given** `PurchaseReconciler`
**When** a purchase is processed
**Then** the sequence is: write to the local pending-ledger → acknowledge → credit exactly once keyed by Play order id → persist → clear pending.
[Source: docs/epics.md#Story-5.2 (AC-1, lines 782-784); docs/architecture.md:496-497 (PurchaseReconciler grants credits exactly once keyed by Play order id), :522 (Purchase data flow: UI → BillingService → Unity IAP → **PurchaseReconciler (pending→ack→credit once→persist)** → CreditService event → UI), :419-420 (PurchaseReconciler is the architecture-NAMED Billing file). **The "credit" step is the EXISTING one-way `ICreditService.GrantCreditsAsync(int)` seam (CreditService.cs:149) — the reconciler does NOT reimplement a grant.** **"Persist" + "clear pending" both mutate `SaveModel.PendingPurchases` through `SaveService.SaveAsync` (the durable ledger that survives an app-kill — PendingPurchaseRecord.cs / SaveModel.cs:77-79 already reserved).** **Acknowledge is a NEW `IStoreAdapter` method (the device-only Play "consume/acknowledge" call) — its real Play wiring is the device-build deferral, the editor `#else` path is a stub-safe no-op success (the `UnityIapStoreAdapter` precedent).]**

**AC-2 (an interrupted purchase — network drop / app-kill before crediting — is reconciled on the NEXT launch and granted EXACTLY ONCE, never twice).**
**Given** an interrupted purchase (network drop / app kill before crediting)
**When** the app next launches
**Then** pending purchases are reconciled and a paid-for pack is granted exactly once (never twice).
[Source: docs/epics.md#Story-5.2 (AC-2, lines 786-788); docs/architecture.md:39,202 (NFR-4 billing integrity — exactly-once), :497 (keyed by Play order id), :510 (NFR-4 → PurchaseReconciler exactly-once). **EXACTLY-ONCE is keyed by the Play order id: a `PendingPurchaseRecord` whose order id is already recorded as granted is NOT re-granted (the dedup invariant — the load-bearing assertion of this story). The pending-ledger write happens BEFORE the grant so an app-kill at ANY point leaves a recoverable record; on launch, `ReconcilePendingAsync` walks the ledger and grants only the not-yet-credited records, then clears them.** **This is the inverse of the 1.7 two-write `FirstLaunchGrant` (where a re-grant is benign) and matches the 1.8 daily-claim "a crash between two persists must not double-grant" discipline — paid Credits are NOT benign to double-grant.]**

**AC-3 (a cancelled or failed purchase leaves the balance unchanged, shows a non-alarming message, and returns the player to their prior context with nothing lost).**
**Given** a cancelled or failed purchase
**When** it resolves
**Then** the balance is unchanged, a non-alarming message is shown, and the player returns to their prior context with nothing lost.
[Source: docs/epics.md#Story-5.2 (AC-3, lines 790-792); docs/architecture.md:38,217,313-314 (NFR-3 typed results, never crash). **5.1 already delivers "cancelled/failed → balance unchanged, no grant, no event, typed `Cancelled`/`StoreUnavailable`" (BillingService.cs:77-83 + the 5.1 tests). 5.2's addition: a cancelled/failed purchase writes NO pending-ledger record (nothing to reconcile — only a `Purchased` store result opens a pending record), so a cancel/fail leaves the ledger AND the balance untouched.** **The "non-alarming message" + "return to prior context" PIXELS are the Epic-6 Shop HUD / the 5.4 top-up sheet (the UI-presenter altitude split — 5.2 surfaces the typed `PurchaseResult`/reason the message binds to, builds no pixels).]**

**AC-4 (a purchase is acknowledged within Play's allowed window — un-acknowledged purchases auto-refund).**
**Given** Play Billing acknowledgement rules
**When** a purchase is made
**Then** it is acknowledged within the allowed window (un-acknowledged purchases auto-refund).
[Source: docs/epics.md#Story-5.2 (AC-4, lines 794-796); docs/architecture.md:496-497 (the reconciler sequence includes "acknowledge"), :522 (pending→**ack**→credit once→persist). **Play Billing auto-refunds a consumable/purchase NOT acknowledged within ~3 days. The reconciler acknowledges via the NEW `IStoreAdapter.AcknowledgeAsync(orderId)` (or a consume) seam BEFORE/at credit time, every reconciliation pass (including the launch recovery pass for an interrupted purchase), so a purchase that was credited-but-not-acknowledged on a prior interrupted run still gets acknowledged on the next pass.** **The REAL Play acknowledge/consume call is the device-build deferral (com.unity.purchasing not imported); the editor `#else` is a stub-safe success. 5.2 PINS the SEQUENCE + the seam invocation (the order is acknowledge-then-clear-pending), proven headless against the fake adapter's acknowledge-call counter — NOT the real Play SDK round-trip.]**

For each record (newest-to-oldest or stable order — document the choice): (1) if `State == PendingGrant`, resolve the pack via `CreditPackCatalog.TryGet(record.PackId)` — an UNKNOWN pack id is a corrupt/stale record: log loudly via `GameLog.Error`, mark it terminal and clear it (do NOT grant a pack that no longer exists, do NOT loop forever); on a known pack, call `ICreditService.GrantCreditsAsync(pack.TotalCredits)` — on success advance the record to `Granted` (persist the state advance so a kill after the grant does not re-grant — the order-id dedup is the SECONDARY guard, the persisted `Granted` state is the PRIMARY one); on a grant `Result.Fail` LEAVE the record at `PendingGrant` (the next pass retries — do NOT clear, do NOT advance) and continue. ### The design decisions this story locks (call them out for the CR reviewer)
1. **The pending-ledger write precedes the grant; the persisted `State` advance is the PRIMARY exactly-once guard, the order-id dedup the SECONDARY (Decision A/B/C).** A `PendingGrant` record is written + persisted BEFORE `GrantCreditsAsync`, so an app-kill at ANY point after the player paid leaves a recoverable row. After the grant succeeds the record advances to `Granted` and is PERSISTED before the acknowledge — so a kill between grant and ack re-runs the acknowledge but NEVER re-grants. The order id is the dedup key (a `Granted`/`Acknowledged` order id is never re-credited). This is the inverse of 1.7's benign-re-grant `FirstLaunchGrant` and matches 1.8's daily-claim "a crash between two persists must not double-grant."
2. **The reconciler shares the economy `SaveMutationLock` (Decision C, the DailyRewardService precedent).** A sibling Billing-tier mutator of the same `SaveModel` (it mutates `Credits` via `GrantCreditsAsync` AND `PendingPurchases` directly) must serialize against `CreditService`/`ProgressionService`/`DailyRewardService` — a per-reconciler lock would let a reconcile write and a credit spend interleave + persist each other's uncommitted deltas. Billing already references Economy, so the lock is reachable; Bootstrap injects the one shared instance.
3. **The reconciler is interposed into `BillingService`'s single grant site WITHOUT a public-surface change (Decision E — the 5.1 seam paying off).** 5.1 put the grant in ONE place (the `Purchased` branch) precisely so 5.2 could swap the bare `GrantCreditsAsync` for `RecordPendingAsync` + `ReconcileAsync` behind the same `PurchaseResult`/`OnPurchaseCompleted` contract. The 5.1 `BillingServiceTests` are the regression proof the surface is unchanged.
4. **`GrantFailed` flips from "lost until 5.2" to "recovered on next launch"; `AlreadyOwned` becomes safely grantable via the dedup (Decision E — the 5.1 seams settle).** The 5.1 `GrantFailed` (paid-but-not-saved) now leaves a `PendingGrant` record the launch pass recovers exactly-once; `AlreadyOwned` (an un-consumed prior purchase) can now be granted-once through the reconciler because the order-id dedup makes it safe (the explicit 5.1 reason to defer). Justify the `AlreadyOwned` call in Task 3 Decision E.
5. **Acknowledge (AC-4) is a SEQUENCE + seam-call invariant, proven headless; the real Play SDK call is device-deferred.** The reconciler calls `IStoreAdapter.AcknowledgeAsync` AFTER the grant, once per `Granted` record, retrying on `false` (the credits are already safe — only the ack is outstanding). The editor `#else` returns a no-op success; the test pins the order + the call-count, not a real Play round-trip (the 5.1 `UnityIapStoreAdapter` stub-safe-editor posture).
6. **The launch recovery pass (AC-2) runs post-load, fire-and-forget, no-op on the common launch (Decision D/F).** It runs AFTER `SaveService.InitializeAsync` (the `RequireModel` before-load contract), does nothing when `PendingPurchases` is empty (the overwhelming common case), and does not block the splash.

### Edge cases & boundary rules (must-handle — these become test cases)
- **Happy path (AC-1):** `Purchased` → write `PendingGrant` (persist) → grant base+bonus ONCE (`GrantCreditsAsync`, advance to `Granted`, persist) → `AcknowledgeAsync` (advance to `Acknowledged`, remove) → ledger empty, `OnPurchaseCompleted` once, `PurchaseResult.Succeeded`.
- **Interrupted before grant (AC-2):** a `PendingGrant` record survives the kill; the launch pass grants it EXACTLY once.
- **Interrupted between grant and acknowledge (AC-2/AC-4):** a `Granted` record survives; the launch pass grants NOTHING (dedup) and only acknowledges + clears.
- **Exactly-once (AC-2, load-bearing):** two `ReconcileAsync` passes over one purchase grant it once total; a `Granted` record's re-pass grant save-count == 0.
- **Idempotent pending-write:** `RecordPendingAsync` twice for one order id → one record.
- **Cancel/fail (AC-3):** no pending record written, balance unchanged, no recovery work.
- **Acknowledge fails (AC-4):** `false` → record stays `Granted` (credits safe), next pass retries the ack, no re-grant.
- **Grant-fault recovery (settles 5.1 `GrantFailed`):** `FailNextSave` on the grant → record stays `PendingGrant`, `GrantFailed` returned, balance net-unchanged → next pass recovers exactly-once.
- **Corrupt/stale ledger record:** unknown pack id → logged + cleared (terminal), no grant, no infinite loop.
- **Empty ledger:** launch pass is a no-op (no grant/ack/save).
- **Ctor null args / no locator:** every ctor arg null → `ArgumentNullException`; no `GameServices.Get` in the reconciler.
- **Before-load:** the launch pass runs AFTER `SaveService.InitializeAsync` (`RequireModel` throws otherwise — the CreditService/DailyRewardService before-load contract).

## Review Findings

Adversarial 3-layer code review (story-cr-fanout — Blind Hunter / Edge Case Hunter / Acceptance Auditor + per-finding verifier, 2026-06-15): **23 raw → 23 deduped (0 cross-layer convergence) → 8 confirmed (8 PATCHED), 2 deferred, 10 spec-sanctioned, 3 false-positive. 0 AC violations.** 433/433 EditMode green re-verified after patching. The 8 confirmed findings clustered on the `PurchaseReconciler` internals the dev tests under-covered: the in-line-purchase result contract (self-contradiction + already-granted ambiguity), the sync-over-async lock helpers, and corrupt-record guards (non-positive total, unrecognized state, empty order id). The recurring root cause: `ReconcilePurchaseAsync` INFERRED its outcome from a re-read state + balance, which a grant↔state-advance fault or a prior-pass grant could confound — fixed by having `ReconcileOneAsync` report the outcome AUTHORITATIVELY.

- [x] [Review][Patch] **`ReconcilePurchaseAsync` returned a self-contradictory result (GrantPending/0 credits with an increased balance) when `AdvanceToGrantedAsync` faulted.** `PurchaseReconciler.cs`. Root-cause fix: `ReconcileOneAsync` now returns a typed `RecordOutcome` (`NewlyGranted` / `AlreadyGranted` / `GrantPending`) reported authoritatively from the grant path, and `ReconcilePurchaseAsync` builds its result from THAT — never from a re-read state + `_credits.Balance`. A grant-then-state-advance-fault now returns `GrantPending` (consistent with the loud-logged client-trusted two-write window).
- [x] [Review][Patch] **`ReconcilePurchaseAsync` reported `CreditsGranted = pack.TotalCredits` even when the record was already `Granted` (acknowledge-pending from a PRIOR pass).** Same root-cause fix: `AlreadyGranted` (this call credited nothing — a double-tap / relaunch race) now maps to `GrantPending`/0, so `OnPurchaseCompleted` never claims a grant this call did not make.
- [x] [Review][Patch] **Sync-over-async: `ReadState`/`SnapshotOrderIds` blocked on `_mutationLock.WaitAsync().GetAwaiter().GetResult()` (a device-path deadlock risk on the non-reentrant lock + a violation of the story's own DailyRewardService `await` discipline).** (2 findings, same root.) `PurchaseReconciler.cs`. Both are now `async` (`ReadStateAsync`/`SnapshotOrderIdsAsync`) using `await _mutationLock.WaitAsync().ConfigureAwait(false)`.
- [x] [Review][Patch] **`ReconcileOneAsync` had no defensive guard for a non-positive `pack.TotalCredits` (would throw `ArgumentOutOfRangeException` out of `GrantCreditsAsync` — an NFR-3 "never throw" violation).** `PurchaseReconciler.cs`. Added a `pack.TotalCredits <= 0` corrupt-record guard (clear + log, never throw), mirroring the unknown-pack guard — defense-in-depth on the factory-guaranteed-positive invariant.
- [x] [Review][Patch] **`FindByOrderId` matched an empty order id (a corrupt pre-5.2 record with `OrderId == ""` could be resolved + acknowledged with an empty id).** `PurchaseReconciler.cs`. `FindByOrderId` now returns null for a null/empty order id; `SnapshotOrderIdsAsync` skips null/empty-id elements rather than indexing `.OrderId` blind.
- [x] [Review][Patch] **`ReadState` silently treated an unrecognized persisted state string (corrupt / forward-version) as `PendingGrant` (could re-credit).** `PurchaseReconciler.cs`. Added a `PendingState.Invalid` (any state that is neither `pending-grant` nor `granted`); `ReconcileOneAsync` clears such a record as corrupt (terminal, never granted), mirroring the unknown-pack guard.
- [x] [Review][Patch] **`ClearRecordAsync` recovery-swap re-add lacked the DailyRewardService-style robustness/coverage.** `PurchaseReconciler.cs`. (Folded into the async-lock + authoritative-outcome refactor; the recovery-swap branch restores the record on the detached model + logs, the established pattern. Covered by the suite's green re-verify — no behavior change, the fragility was the undocumented list-independence assumption, now consistent with the other lock spans.)
- [x] [Review][Defer] **TOCTOU race: two concurrent in-process reconcile passes on the same order id could both grant (the lock is released across `GrantCreditsAsync`).** Out-of-scope: AC-2 scopes exactly-once to NEXT-LAUNCH (sequential process restart) recovery, not concurrent in-process overlapping calls; the persisted-`Granted`-state guard defends the sequential app-kill path the story targets. A concurrency guard (an in-memory in-flight-order set, or serializing the launch pass against the in-line path) is a separate hardening concern. Owner: a future Billing concurrency-hardening story / the Phase-2 verifier. → deferred-work.md.
- [x] [Review][Defer] **`ClearRecordAsync` can loop indefinitely on unrecoverable save-file corruption (the catch logs Warn + retries next pass forever).** Out-of-scope: this is the spec's sanctioned retry-on-fault pattern (matching the grant-fault + ack-fault branches); a persistent save-layer corruption is a Persistence/recovery concern, and the MVP is client-trusted (no server verifier to break the loop). A retry-count abort on `PendingPurchaseRecord` is Phase-2 hardening. Owner: Phase-2 server verification / a save-recovery hardening pass. → deferred-work.md.
