# Story 4.3: Scan a Monster for free

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to scan a Monster at no cost,
So that I learn about it and progress its Codex entry without spending.

## Acceptance Criteria

**AC-1 (information is revealed on Scan).**
**Given** a settled Monster in an encounter
**When** the player taps Scan
**Then** information about the Monster is revealed (the Scan records the `Scanned` flag for the Monster, and the result carries enough for the HUD to surface the revealed info — the chunky reveal pixels are Epic 6).
[Source: docs/epics.md#Story-4.3 (lines 650-652); docs/epics.md:30 (FR-7 — Scan reveals information and progresses the Codex entry at no Credit cost; never changes Credit balance); docs/architecture.md:28 (Lure → Scan/Capture/Slay), :68 (Scan and base Capture remain free), :252 (EncounterService state machine Lure/Scan/Capture/Slay). The `CodexEntryData.Scanned` flag already exists (CodexEntryData.cs:13); Story 2.5's `CodexEntryView.Scanned` already surfaces it.]

**AC-2 (partial Codex data is recorded — even before Capture/Slay).**
**Given** a Monster that has not yet been captured or slain
**When** the player scans it
**Then** partial Codex data is recorded (the `Scanned` flag), and it is recorded EVEN BEFORE a Capture/Slay discovery — i.e. a Scan can record scan-progress on a Monster the player has not yet "discovered" via Capture/Slay.
[Source: docs/epics.md#Story-4.3 (line 652 — "partial Codex data is recorded even before Capture/Slay"); docs/architecture.md:187 (codex stores scanned/captured/slain + variant flags), :475 (state-faithful restoration preserves per-monster scan progress). **DESIGN DECISION (Decision B below): does setting `Scanned` create a Codex KEY (→ counts as discovered in X/67)? Resolution: a Scan records the `Scanned` flag WITHOUT incrementing the X/67 discovered count — Scan is partial progress, NOT a discovery (the [[ux-feed-upstream-queue]] OQ-7 hybrid-reveal model + the `DiscoverySource` enum's verbatim "scanning does not discover" rule). See Decision B for the exact persistence shape.**]

**AC-3 (the Credit balance NEVER changes — Scan is free).**
**Given** any Scan attempt (success, repeat, or a Monster already scanned)
**When** the Scan resolves
**Then** the Credit balance never changes — Scan costs no Credits and no charges; it is a free action.
[Source: docs/epics.md#Story-4.3 (line 652 — "the Credit balance never changes"); docs/epics.md:30 (FR-7 "never changes Credit balance"); docs/architecture.md:68 (Scan free); CLAUDE.md Economy canon ("Scan and base Capture are free" — Credits buy ONLY Basic Lure / Premium Lure / Multi-Lure / Slay). Mutation-testable: any path that touches `model.Credits` or a charge on a Scan → red.]

## Dev Notes

### SCOPE — read this first
This is the SECOND FR-6–10 gameplay story (after 4.2 Lure). It adds the **Scan** action — a FREE (no-credit, no-charge) in-encounter action that records partial Codex progress (the `Scanned` flag / in-encounter scan-state) and reveals info. It composes the inherited 4.1 atomic-write pipeline as a THIRD sibling (after the charge-spend `CommitActionAsync` and the credit-spend `CommitLureSpendAsync`): a FREE composed write that persists ONLY a codex/encounter scan delta in ONE `SaveAsync`. It DEFERS the persisted scan-progress disk snapshot to 5.4 and the reveal UI to Epic 6.

1. **`CodexService.StageScan`** — a lock-free, persist-free `Scanned`-flag sibling of `StageDiscovery`, with the SAME rollback fidelity + idempotency, but it does NOT raise `OnMonsterDiscovered` and does NOT count as a discovery (Decision B — scan ≠ discover).
2. **`EncounterService.TryScanAsync(monsterId)`** — the public free action: drive `Lured → Acting → Resolving → Lured`, ONE atomic codex/encounter-scan persist (copying the 4.1/4.2 pipeline, NO economy mutation, whole-mutation rollback), return a typed `ScanResult`. NEVER touches Credits or charges (AC-3).
3. **Decision B (the design crux): a Scan records partial progress WITHOUT inflating X/67** — Model B1 (recommended): record undiscovered-monster scan progress in the encounter state (`EncounterMonsterStateData.ScanProgress`, persisted by 5.4) + flip the persistent `CodexEntryData.Scanned` flag only on already-discovered monsters; keeps "key-presence == discovered" inviolate.

- **BUILD now:** `CodexService.StageScan` (the `Scanned`-flag staged delta, no discovery event); `EncounterService.TryScanAsync` + the FREE composed write (copy the 4.1/4.2 pipeline, drop ALL economy mutation, keep the lock+single-persist+rollback shape); the `Lured → Acting → Resolving → Lured` sequencing (reuse/extend `RunActionAsync` for a charge-free, discovery-free action — Decision E); a typed `ScanResult`; the in-encounter scan-state record (Decision B1); the `Encounter.Tests` AC-1–3 pins; deferral bookkeeping + any upstream clarification.
- **DEFER to Story 5.4:** the persisted scan-progress disk snapshot/rehydrate (the state-faithful round-trip of `ScanProgress` across Shop/relaunch).
- **DEFER to Epic 6:** the Scan reveal UI (revealed-info render, partial-Codex reveal animation, the action-bar Scan affordance).
- **Do NOT:** add a `Scan` member to `DiscoverySource` (scan ≠ discover — the enum forbids it); raise `OnMonsterDiscovered`/`OnCodexCompleted` on a Scan; increment `DiscoveredCount` / create a discovered key for a scan-only on an undiscovered monster (Decision B1); mutate `model.Credits` or any charge in the Scan path (AC-3 — free action); call `GameServices.Get<T>()` in Encounter/CodexService (AR-4); do two `SaveAsync` for one Scan (AR-8); skip the shared `SaveMutationLock` (a Scan still mutates the shared `SaveModel`); build the reveal UI (Epic 6) or the disk snapshot (5.4).

### The design decisions this story locks (call them out for the CR reviewer)
1. **Scan is a FREE composed write — the THIRD sibling of the 4.1 atomic-write pipeline (Decision C).** After the charge-spend (`CommitActionAsync`, 4.1) and the credit-spend (`CommitLureSpendAsync`, 4.2), Scan adds a no-economy composed write: shared lock, capture-model-once, ONE `SaveAsync`, recovery-swap guard, whole-mutation rollback, events-after-release — but the ONLY in-memory mutation is the scan stage (no `Credits`, no charge). It STILL takes the shared lock (it mutates the shared `SaveModel`).
2. **Scan ≠ discover (Decision B — the crux).** Setting `Scanned` does NOT make a monster "discovered" for the X/67 count and does NOT raise `OnMonsterDiscovered`. Model B1 (recommended): undiscovered-monster scan progress lives in the encounter state (5.4 persists it); the persistent `CodexEntryData.Scanned` flag is flipped only on already-discovered monsters. This keeps CodexService's canonical "key-presence == discovered" rule (CodexService.cs:74-75) inviolate while satisfying AC-2's "partial data recorded even before Capture/Slay." The `DiscoverySource` enum's verbatim "scanning does not discover" rule is honored.
3. **`CodexService.StageScan` is the `Scanned`-flag home (Decision A) — a lock-free sibling of `StageDiscovery`.** The codex-write RULES stay in CodexService (one home); it returns a staged delta with `StageDiscovery`'s exact rollback fidelity (the three `RollBack` cases) + idempotency (already-scanned → no-op), but with NO discovery event raise.
4. **A typed `ScanResult` (Decision D), not `SpendResult`.** A Scan does not spend, so `SpendResult.NewBalance` is meaningless; `ScanResult { Success, FailureReason, MonsterId, AlreadyScanned }` is self-describing (the 4.2 `LureResult` precedent). Typed-result-not-throws; throw only for a null/empty monster id.
5. **Out-of-sequence Scan gets a distinct `NotSettled` reason (Decision E), partially settling the 4.1 deferral (deferred-work.md:21).** A Scan called outside a live encounter returns a typed `NotSettled`/`NotInEncounter`, NOT the misleading inherited `PersistenceFailed`+0.

### What this story IS and IS NOT
- **IS:** (a) `CodexService.StageScan` (the `Scanned`-flag staged delta, no discovery event, full rollback fidelity); (b) `EncounterService.TryScanAsync(monsterId)` + the FREE composed write (4.1/4.2 pipeline, NO economy mutation, ONE persist, rollback); (c) the `Lured → Acting → Resolving → Lured` sequencing for a charge-free/discovery-free action; (d) a typed `ScanResult`; (e) the in-encounter scan-state record (Decision B1); (f) the `Encounter.Tests` AC-1–3 pins; (g) deferral bookkeeping + upstream clarification.
- **IS NOT:** the persisted scan-progress disk snapshot (5.4); the Scan reveal UI / partial-reveal animation (Epic 6); a `DiscoverySource.Scan` member (forbidden); a discovery event on Scan; an X/67 increment on a scan-only undiscovered monster (Decision B1); any Credit/charge mutation on Scan (AC-3); a second `SaveAsync` per Scan (AR-8); a `GameServices.Get` in Encounter (AR-4).

### Architecture constraints (hard rules)
- **One transactional write per player action (AR-8, architecture.md:644-649, :328).** The Scan's codex/encounter-scan delta commits in ONE atomic `SaveAsync`; a persist failure rolls the WHOLE in-memory mutation back; NEVER two persists per Scan. [architecture.md:644-649]
