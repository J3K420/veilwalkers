# Story 3.4: Detect planes and anchor objects with occlusion and lighting

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want objects to rest convincingly on my real surfaces,
So that the AR illusion holds.

## Acceptance Criteria

**AC-1 (a detected plane anchors the object; occlusion + environmental lighting hold the illusion).**
**Given** plane detection (`PlaneAnchorService`)
**When** a surface is detected and an object is placed
**Then** it rests on a detected plane (floor/table/ground), is occluded by real-world foreground objects where depth supports it, and is environmentally lit.
[Source: docs/epics.md#Story-3.4 (AC-1); docs/architecture.md:408 (PlaneAnchorService — FR-4 anchoring/occlusion/lighting + guidance), :466-468 (AR boundary — thin adapter, no branching), :229-230 (URP + AR occlusion + environment lighting), :144 (URP for occlusion/lighting); FR-4]

**AC-2 (no plane yet → friendly coaching, and NO object is spawned into empty space).**
**Given** no plane has been found yet
**When** the player aims
**Then** friendly coaching is shown ("Move your phone slowly across a textured surface") and no object is spawned into empty space.
[Source: docs/epics.md#Story-3.4 (AC-2); docs/architecture.md:408 (PlaneAnchorService "+ guidance"), :217 (user-facing guidance, never uncaught exceptions — NFR-3), :38 (NFR-3 — AR failures degrade to guidance); FR-4; NFR-3]

**AC-3 (spawning is pooled + capped under URP, targeting ≥30 FPS sustained on mid-range).**
**Given** the performance budget (NFR-1)
**When** objects spawn
**Then** spawning uses `MonsterSpawner` object pooling with capped concurrent spawns under URP, targeting ≥30 FPS sustained on mid-range devices.
[Source: docs/epics.md#Story-3.4 (AC-3); docs/architecture.md:410 (MonsterSpawner — object pooling, spawn caps), :229-230 (object pooling for monsters, capped concurrent spawns), :509 (NFR-1 → MonsterSpawner pooling + URP); NFR-1; SM-6 plane-anchor success :597]

## Dev Notes

### SCOPE — read this first

### The design decisions this story locks (call them out for the CR reviewer)
1. **The inherited `ArcoreSession` device-glue deferral is CARRIED FORWARD to Story 6.3, not settled here (decision #1).** The 3.3 dev deferral named "Story 3.4 (AR rig + plane detection) / Story 6.3 (scene placement)" as the owner of `ArcoreSession`'s device subsystem `#if` stub. 3.4 builds the plane/anchor/spawn LOGIC but — like 3.1/3.2/3.3 — builds NO scene; the AR Foundation `ARSession`/`ARPlaneManager`/`ARAnchorManager` are scene `MonoBehaviour`s, so the device subsystem glue is genuinely blocked until the AR rig SCENE exists (Story 6.3). 2. **Plane/anchor/occlusion/lighting/spawn split into pure-logic DECISIONS vs device/scene GLUE.** The architecture's "AR contains no branching logic worth testing — thin adapter" (architecture.md:466) is reconciled the same way 3.1/3.2/3.3 did it: the DECISIONS genuinely worth testing (coaching-vs-place, the cap, pooling reuse) live in pure-logic `PlaneAnchorService`/`MonsterSpawner`, headless-tested against fakes; the GLUE the mandate targets (the real plane subsystem, occlusion shader, light estimation, URP prefab pool) lives in the thin `#if` adapters and is stubbed-and-deferred. 3. **AC-2 "no object is spawned into empty space" is a load-bearing guard, not just copy.** `PlaneAnchorService.TryPlace()` checks `HasTrackablePlane` FIRST and refuses to even ask for a placement pose / create an anchor when no plane is tracked — the AC-2 pin is `GetPlacementPoseCalls == 0 && CreateAnchorCalls == 0` with no plane (mutation-testable). 5. **`Pose` is the headless-safe placement type.** The seam/service/fake use `UnityEngine.Pose` (a plain position+rotation value), NOT any AR-Foundation trackable type — so the placement decision is fully testable in EditMode and the `AnchorToken` (`Core.Contracts`, already defined Story 1.2) is built from the pose+planeId. 6. **The restore path is explicitly 3.5's — and 3.5 ABSORBS 3.4's create-anchor seam, it does NOT add a parallel one.** 3.4's seam is `IArPlaneAnchorProvider` (forward: detect → pose → create anchor). The `IArAnchorProvider.TryRestoreAnchor` surface (architecture.md:409) + `RelocatedToPlane` (architecture.md:471-473) + `AnchorToken.IsValid` (1.2 CR deferral) are Story 3.5 — do NOT pre-build them. **Reinvention guard:** the architecture names ONE anchor seam `IArAnchorProvider` (architecture.md:409) owning BOTH save (→`AnchorToken`) AND restore, and 3.5's AC-1 (epics.md:574-576) is the SAVE half — which is the SAME native create-anchor op as 3.4's `TryCreateAnchor`. ### Edge cases & boundary rules (must-handle — these become test cases)
- **No plane → coaching, NO spawn (AC-2):** `HasTrackablePlane = false` → `TryPlace()` = `NeedsCoaching(CoachingMessage)`, `GetPlacementPoseCalls == 0`, `CreateAnchorCalls == 0`. THE load-bearing AC-2 pin.
- **Plane found → placed + anchored (AC-1):** `HasTrackablePlane = true` + pose + successful anchor → `Placed(token)`, the token matches the fake's pose+planeId, `CreateAnchorCalls == 1`.
- **Plane tracked, no pose right now (AC-1/NFR-3):** `HasTrackablePlane = true` but `TryGetPlacementPose` false → `NeedsCoaching`, `CreateAnchorCalls == 0`, no throw.
- **Anchor creation fails (NFR-3):** pose returned but `TryCreateAnchor` false → `Failed` + `GameLog.Warn`, no throw.
- **Spawn cap enforced (AC-3):** N spawns succeed (`ActiveCount == N`); the (N+1)th refused, `InstantiateCalls` did not exceed N, cap warning logged. No over-spawn.
- **Pooling = reuse (AC-3):** spawn → release → spawn reuses the freed instance: `InstantiateCalls` stays 1, `ActivateCalls == 1`, `ActiveCount == 1`. No second instantiate.
- **Release safety (NFR-3):** unknown/out-of-range handle + double-release → `GameLog.Warn` no-op, `ActiveCount` not negative, no throw.
- **View inert (service unregistered / services not ready):** `RequestPlacement()` no-op + `GameLog.Warn`, never throws at `Awake` (the 2.4/2.5/3.1/3.2/3.3 graceful-degrade precedent).
